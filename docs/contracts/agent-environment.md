# Canonical agent environment

Owner: [#214](https://github.com/RepairYourTech/SymbioteIDE/issues/214), consuming #179 portable Projects and #184 runtime contracts. `symbiote-config::environment` represents desired resources and computes an effective environment without reading native configuration, writing files, installing resources, loading hooks or launching a worker.

Projects can embed named `agent_environments` in the portable manifest. Each environment carries its own schema version and the same canonical Project identity as its manifest. A declaration for another Project is rejected. Existing v1 manifests without this optional field remain valid and serialize without it. Older readers that do not understand the field reject it; they must not discard it or rewrite a Project using a partial view. Unknown environment versions require an explicit migration; there is no automatic downgrade.

The manifest parser now rejects duplicate keys recursively before map deserialization and limits input to 1 MiB. This prevents repeated environment/resource/extension names from silently collapsing. Canonical pretty serialization is also bounded; if expansion would exceed the parser limit, export fails explicitly rather than producing an unreadable manifest. Structural schemas are generated by `cargo run -p symbiote-config --example config_schema`; semantic validation still applies after parsing.

## Intent and local facts

The desired document describes resource identity, kind, version, trust, ownership, lifecycle and selectors. Payloads and secrets use symbolic references rather than executable commands, inline credential values or machine paths. The new environment extension channel also carries references, not arbitrary executable JSON. These restrictions cannot detect a user deliberately mislabelling a secret as an identifier; callers must preserve the distinction and resolve secret handles only in authorized local state. Existing Project extensions remain opaque and must not be treated as a safe channel for secrets or execution.

Core policy references remain separate from pluggable resources. An instruction, skill, hook or plugin cannot rewrite task lifecycle, fixed staffing, billing, permission enforcement or mandatory completion gates through this resolver. Native and external runtimes consume the same resource intent; no harness receives implied MCP or tool access because another Role uses it.

Resolution is read-only and depends on an explicit target plus compatibility and Host feasibility facts. A supported resource is not automatically authorized for execution. Host permission enforcement, credential entitlement, dispatch persistence, compatibility freshness and the actual native format remain separate gates. Native config projection belongs to #187; preventive sandbox enforcement belongs to #218. No native `.codex`, `.claude`, `.pi` or other path is inferred here.

Specificity increases from user-global through Project, Role, Binding, Task, Dispatch, Runtime Profile and Host. Sorting is independent of input order. Conflicting declarations at the same specificity remain conflicts; a higher layer cannot replace or disable an earlier required resource. Inherited declarations retain the earlier definition. Host facts bind to the exact target and resource declaration, including version and payload, and explicitly establish mode support. They are trusted caller inputs, not deserializable portable authority. Delegated grants must stay within the independently established parent ceiling.

Required resource issues block the plan. Unsupported or untrusted optional resources remain visible with issues and are excluded by `EffectiveResource::is_eligible()`. Consumers must check the global blockers as well as individual eligibility before even preparing a projection; neither check authorizes execution. Core-policy and extension approvals remain explicit. Limits are 128 layers/policy references/extensions, 4096 resource declarations, 128 grants per resource and 128 bytes per symbolic resource reference.

## Persistence, recovery and verification

The existing Project three-way merge handles desired environment changes. Conflicting edits retain a conflict record and cannot finish until resolved, including simultaneous changes to profile mode. No native files or temporary grants are created, so this batch has no executable bootstrap rollback. Later projection must preserve unmanaged and concurrently edited files and revoke temporary grants on failure; those acceptance requirements remain open.

Run `cargo test -p symbiote-config --locked` for environment resolution and manifest integration fixtures. Fixtures certify canonical semantics, not Claude, Codex, Pi, OpenCode or native compatibility. Real version-bound adapter dossiers, native shapes, installation/projection, unmanaged-file preservation, dispatch integration and runtime recovery remain pending. #214 is not closed by these contracts.

Inspect the supplied deliberately unverified intent with:

```sh
cargo run -p symbiote-config --example environment_plan -- \
  crates/symbiote-config/fixtures/environment/project.json development \
  crates/symbiote-config/fixtures/environment/target.json
```

The inspector supplies no compatibility, mode-support, approval or grant facts and prints the resulting blockers. It neither probes a runtime nor writes a native file. Its success exit means inspection completed, not that the plan is executable.

This pure Rust library has no UI accessibility surface and performs no inference or credential changes. Full Linux/Windows/macOS runtime and workbench evidence remains with the corresponding integration owners.
