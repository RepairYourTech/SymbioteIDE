# Client/Host protocol v1.14 foundation

Canonical owner: [#181](https://github.com/RepairYourTech/SymbioteIDE/issues/181), depending on #36 and #176. `symbiote-protocol` defines the narrow Project/task/journal request boundary used by the initial durable Host. This is not full #181 acceptance. It reuses canonical domain IDs, Project/Root/Role/Task/ChangeStream models and does not introduce a second lifecycle authority.

## Wire contract

Each `Request` contains exact `version: {major: 1, minor: 14}`, `correlation_id`, `command_id`, and an internally tagged `operation`. v1.14 adds `observe_root_placement` (Host-verified recording of a canonical Root's repository placement: the claimed Host identity must be the daemon's own inventory identity, the canonicalized path must observe as a git work tree on it, and the mutation advances the Root revision under exact CAS; client-declared placements remain refused at registration). v1.13 added `run_started_dispatch` (worker activation of an already-started dispatch through the Host runner: worktree provisioning — reservation verify, base-commit validation against the stream's recorded base, materialization — runs before any transport is built, and with no reservation base or transports configured the Host refuses with typed errors rather than executing anything). v1.12 added `request_task_completion` (worker evidence routing). v1.11 added `start_prepared_task`. v1.10 added [dispatch preparation](dispatch-preparation.md) operations. v1.9 added the durable [provider registry](provider-registry.md) operations. v1.8 added durable [task leases](scheduling-leases.md) and the explainable scheduling projection. v1.7 added typed [Task dependency](work-hierarchy.md) operations (`set_task_dependencies`, `get_task_dependencies`). v1.6 added deterministic [Role routing](role-resolution.md) operations (`resolve_route`, `record_route`, `get_route`). v1.5 added durable [workforce binding](workforce-bindings.md) operations and readiness reports. The owner-authorized [Host pulse](host-inventory.md) from v1.4 and [Project Team](project-team.md) operations from v1.3 remain supported. Canonical work and explicit Task origins from v1.2 remain supported; see [work hierarchy](work-hierarchy.md). Existing resource consent operations remain supported; see [resource consent](resource-consent.md). Framing is transport-owned. Requests are limited to 65,536 bytes and reject unknown/duplicate struct fields, unsupported versions, invalid IDs, page bounds and typed drafts. Error messages do not echo inputs or internal paths.

`hello` offers 1–16 explicit protocol versions. Only v1.14 is supported; both the envelope and offer must include it. Older strict clients cannot decode the new events/capabilities and their Task drafts lack required origins. Upgrade the CLI and daemon together; no downgrade or silent field dropping is provided. `health` returns the negotiation/capability description only. Advertised operations describe protocol availability, not caller grants. Fixtures verify v1.14 and rejection of old/future versions.

`Response` carries `version`, optional `correlation_id`, and `result`, using `{ "Ok": { "kind": ..., "data": ... } }` or `{ "Err": { "code": ..., "message": ... } }`. A correlation ID is absent when parsing fails before a trusted envelope is decoded. Successful response kinds include `resource_consent` alongside existing metadata responses. `encode_response` caps output at 1 MiB before larger allocation. Oversized pages fail as `resource_exhausted`; reduce page size rather than truncate canonical events.

Generate the authoritative request/response/telemetry schemas with `cargo run -p symbiote-protocol --example protocol_schema`. The test suite contains a literal golden v1 request and error-response fixture. Rust types and JSON Schema share the same derives; no generated desktop/WebSocket client is claimed yet.

## Trusted authority and mutation boundary

`Principal` is server-created and has no serde implementation. `Principal::restricted` grants explicit operations per Project. `Principal::local_owner` is an explicit bootstrap policy for a server-authenticated same-UID local owner; it must never be derived from a claimed JSON actor, user, Host ID, permissions field, loopback origin or mere connection success. Only that local-owner policy grants shutdown. The actual peer-credential transport belongs to the Host crate, not this pure protocol library.

`authorize` validates each operation and Project. A GetTask lookup also requires `authorize_task_resource` against the *stored* task's Project before any data is returned; the caller's project_id does not establish resource ownership. Storage must check referenced roots/Roles and Project lineage inside the same transaction as mutation. Each journal page validates event/payload Project lineage and typed nested records before transport output.

Project registration accepts a `ProjectDraft` with proposed identity/name/Lead plus canonical Root/Role records. Roots/Roles must have revision zero, unique IDs and matching Project identity; roots cannot carry machine Host paths. `into_records(principal, server_timestamp)` creates revision-zero active Project/provenance from the authenticated User. No wire owner, Actor, disposition or provenance field exists. Registration commits the Project, Roots and Roles atomically in storage.

Task creation accepts proposed domain identities, a versioned Task contract reference and an initial independent Change Stream declaration. `TaskDraft::into_records()` constructs a Ready Task and Active Change Stream with empty histories. Storage commits both atomically and verifies existing Project/root/Role relationships and worktree/branch conflicts. Declared worktree/branch references do not create filesystem state or grant execution permission. No wire task-history, dispatch, Actor, completion evidence, lifecycle application or journal-append operation exists. Worker completion requests, cancellation and all lifecycle commands remain absent until their authenticated Host authority path exists.

## Retry, durable pagination and telemetry

`command_id` is the durable idempotency key. Retries retain it while correlation IDs may change. Storage must bind identity to authenticated intent and return the original receipt for identical intent, rejecting different intent as `idempotency_conflict`. Server timestamps are not regenerated into a conflicting registration on retry: the Host must recover the original durable timestamp before compiling repeated intent. A `Receipt` returns `sequence`, canonical `revision` and `replayed`; pure protocol types do not themselves persist deduplication state.

`read_journal` carries an exclusive `after` numeric cursor and `limit` in 1–100. A page returns typed durable `JournalEvent` records, `next_cursor` and `has_more`. Events may have global sequence gaps from other Projects; within the selected Project they must strictly increase. The next cursor is the last returned event, or the original cursor for an empty page. Clients acknowledge only consumed pages. Storage determines cursor availability and retention boundaries; protocol cannot fabricate missing history or turn telemetry into a durable event.

Durable payloads are `project_registered`, `task_created` and `task_changed`, retaining canonical records and command identities. These are server output, never wire-authorized commands. `Telemetry` is a separate lossy type with heartbeat/queue-depth observations, no durable cursor and no arbitrary harness payload. No actual streaming subscription/backpressure/heartbeat service is implemented here.

## Evidence and remaining acceptance

Contract tests cover golden serialization, malformed/oversized/exact-limit frames, unknown/duplicate fields, spoofed principals/provenance, unsupported version offers/envelopes, scope and loaded-resource authorization, forbidden lifecycle/evidence import, initial domain states, Project registration consistency, cursor ordering/pagination bounds, telemetry separation and bounded response serialization. Real restart/deduplication/atomicity/peer-credential behavior must be evidenced by Host/store integration tests, not counted from these pure fixtures.

Pending #181: authenticated WebSocket/LAN/mobile transport equivalence; generated runnable clients; live subscriptions and snapshot+delta resynchronization; long-running operation/cancellation semantics; blob transfer; complete permissions for roots/secrets/models/entitlements; providers/native/runtime/goal/delegation/analytics/learning capabilities; leases/fencing/failover; compatible deprecation/migration beyond initial v1.0. UI disconnect does not produce any protocol mutation, completion or budget reset.

Applicability: security/privacy are required at peer authentication, operation/resource authorization, response redaction and credential boundaries. This crate verifies typed boundaries only. Accessibility is not applicable to a headless wire library; actionable error presentation remains a client obligation. Request/response/page caps are tested resource bounds, not performance benchmarks. The pure contract is OS-independent; actual Windows/macOS/Linux transport equivalence is separately pending. No persisted schema migration is performed by this crate; future revisions require an explicit compatibility/rollback policy and tests before changing persisted wire assumptions.
