# Architecture decision contracts (#173)

`symbiote-architecture` provides executable in-memory decision lifecycle, immutable version pins, selective invalidation and predeclared spike contracts. It consumes the #170 product constraints accepted in ADR-0001. It does not select Tauri, SurrealDB, control-plane storage or a provider entitlement.

## Module layout

One concern per file, and each module reads the others only through their public surface:

| Module | The one thing it owns |
| --- | --- |
| `lib.rs` | the crate root: the shared vocabulary (`ContractError`, `Result`, `require`, `text`), `workspace_root`, the module map, and the re-exports consumers name |
| `policy.rs` | the engine — decision states, authority, evidence, version pins, compatibility facts and the `DecisionRegistry` that owns them, plus the published name of every state. It reads no file and no clock |
| `ledger.rs` | this repository's `decisions.json`, in one file: its shape, and the replay that requires each record to publish the state and revision the engine reaches |
| `spike.rs` | the contract concern: `SpikeContract`/`Measurement`, the committed `spike-contracts.json`, the `Run`/`Results` shape, and every rule a run set must meet |
| `repository.rs` | what cargo reports — workspace members, the dependencies they declare, and the content hash of a file in the tree |
| `checks/mod.rs` | the join: `Problem`, and the `problems` entry point that asks the three subjects in ledger order |
| `checks/records.rs` | what the ledger says about its own records and facts — the text and evidence bytes it cited, the owner an open choice names, and a fact whose window lapsed |
| `checks/artifacts.rs` | what the workspace must show for what the ledger publishes — gate status, membership in both directions, pins, and the reach of a provisional choice |
| `checks/contracts.rs` | what the contracts and their runs must show — the contract/decision link, obligation ownership, the bar the choice names with every clause of it answered in the record's own words, and the run set a settled choice stands on |

Refusals keep one owner too: a rule about a record lives with the records, a rule about the tree lives with the artifacts, and a rule about proof lives with the contracts. Two test names in `tests/governance.rs` — `acceptance_requires_new_pin_and_freezes_content` and `supersession_invalidates_only_dependent_artifacts` — are bound by the constitution ledger's catalog, so they cannot be renamed or moved while #170's catalog cites them. Every lower-case name this document writes in a code span with an underscore is either a case this crate's suite runs or one of the names the check lists as not cases — a field, a method or a function, under which no case can be run — and `the_contract_document_names_only_cases_this_crate_holds` holds both directions: each name it reads must be a case the suite runs or a listed name, each listed name must be one the crate's own `src/` carries as a name, not as a fragment of a longer one, *and* one this document still cites, so a name the crate never names cannot be written here, a helper cannot stand in for a case, and a listed name cannot outlive the sentence that needed it. What it reads is a code span, and what it holds is the name: a name written outside one is not read, and finding a case by that name says nothing about whether that case is the one the citing sentence needed.

## Public contract

Proposals start at revision 1. Draft edits require the exact current revision. Draft revision cannot accept a decision. Acceptance is a separate operation: Worker authority is rejected, high reversal cost requires measured-evidence metadata or an explicit Client exception, and every compatibility pin must resolve to fresh verified metadata. Accepted/terminal content cannot be edited; replacements create a new identity and superseding lineage. Supersession validates before changing either record, including concurrent replacement conflicts. Caller retries with stale revisions receive conflict errors without another mutation.

Implementation artifacts pin exact accepted decision revisions and compatibility fact revisions. `require_ready` refuses provisional, unknown, rejected, superseded and stale dependencies. A changed fact or superseding decision returns the sorted affected artifact identities. Unrelated artifacts stay valid. Evidence expiry is evaluated on each gate call; acceptance alone cannot permanently bless an expiring vendor fact. Preserve the caller's approval identity and exception rationale for audit.

`SpikeContract` requires hypothesis, workload, the platforms it applies to, platform/hardware prose, method, finite numeric thresholds, stop conditions, result artifact, cleanup, and the bar it answers (`answers`: one entry per clause it answers, carrying that clause's own words and saying what answers them). Schema v1 rejects unsupported versions and unknown fixed fields. Generate structural JSON schemas with `cargo run -p symbiote-architecture --example architecture_schema`. The schemas describe serialization; runtime validation additionally checks cross-field policy. No previous persisted schema exists: v1 is the initial version, future versions are rejected rather than guessed or downgraded. Two shapes have moved without a second version. In #601 a contract stopped naming the section it answers (`obligations` is refused) and the choice's record began carrying `proof_section`; in #607 an answer stopped naming its clause by a number and began carrying the clause's own words. Version 1 absorbs both moves for the reason the result schema gave when its own shape changed in #600 — no contract document exists outside this repository and this crate is the only reader of the one in it, so there is nothing to migrate — and a document of either old shape — or of both at once — is refused *naming what moved* rather than only the field it is missing: the section went to the choice's record and what answers each clause is the contract's `answers` (`a_contract_document_of_the_shape_before_the_bar_moved_is_refused_naming_what_moved`, and `a_contract_document_holding_the_old_field_beside_its_answers_names_the_move` for the field left beside those answers, which the field list used to answer instead), and a `clause` is now the accepted section's words rather than a position in its split (`a_contract_document_that_names_a_clause_by_its_number_is_refused_naming_what_moved`), with both moves named together when one document carries both (`a_contract_document_carrying_both_old_shapes_at_once_names_both`). Rollback is this repository's own revert of the document and its ledger record, since neither has a consumer outside the crate.

## The repository's own decision ledger

ADR-0001's decisions are also committed as data in [`decisions.json`](../architecture/decisions.json), because a record that exists only as prose cannot refuse anything: before it existed, this crate's registry had no caller in this repository and every pin was a fixture. The ledger holds one record per decision, the compatibility facts they depend on, and one pin record per workspace member.

A decision record holds the `draft` it published from, the `published` state and revision the repository claims, the accepted text it interprets (`record`, with its `record_sha256`), the `acceptance` that made it accepted, the `blocking_issue` that owns whatever decides a choice that is still open, the `proof_contract` that would settle it together with the `proof_section` of its accepted text that says what that proof must do, and the `proposed_dependencies` a dependent implementation would express the choice with. An artifact record holds its `pins` and the gate `status` this repository publishes for it. `Ledger::registry` replays the file through the crate's own transitions — propose, accept, draft revision, fact revisions, pins — and then requires every record's published state and revision to be the ones the replay reaches, so the ledger cannot record a lifecycle this crate would refuse.

Refusals, each naming its subject:

| Refusal | Why it exists |
| --- | --- |
| a schema version this loader does not replay, an unknown field, or no decision at all | a ledger that cannot be read is not a passing ledger |
| a record's text is not in the tree, or has changed since the record cited it | an accepted decision is the text it was accepted from |
| the same for evidence a decision cites | observed evidence is content-addressed; an `https://` reference is recorded, not fetched |
| a record that is still open — `proposed` or `investigating` — with no `blocking_issue`, or a decided one that still names one | an unresolved choice must have an owner |
| a `published` state or revision the replay never reaches | Worker authority, missing measured evidence on a high-reversal-cost choice and invented revisions fail here |
| an artifact `status` that is not the one `gate` reaches, a settled artifact naming a blocking issue, or an unsettled one naming none | the readiness this repository publishes is the one the registry computes |
| a workspace member cargo reports with no record, or a record for a path cargo does not report | a new member must declare what it depends on, and the ledger cannot pin a crate that does not exist |
| a member that declares one of a decision's `proposed_dependencies` without pinning it, or pins it while declaring none of them | an unresolved choice may not reach implementation unrecorded |
| a compatibility fact whose validity has lapsed | vendor facts expire independently |

`cargo test -p symbiote-architecture` runs the ledger suite, and `cargo run -p symbiote-architecture --example decisions` prints the published map — every decision with its state, revision and owners, every artifact with its status, pins, reasons and blocking issue — and exits non-zero while a refusal stands.

## The repository's own spike contract

#38's proof obligations are committed as data in [`spike-contracts.json`](../architecture/spike-contracts.json), because a bar that lives only in prose is a bar chosen after the measurement. One contract, `#38/desktop-shell-representative-workload`, settles `ADR-0001/DESKTOP-SHELL`: its hypothesis, the representative workload, the platforms it applies to as data, the reference hardware, the measurement plan, eleven predeclared ceilings, the stop conditions and the cleanup, with every obligation tagged by the issue that owns it. The decision record names the contract back, so the choice and its proof cannot drift apart silently, and the contract points at the run that would settle it — `docs/proofs/results/desktop-shell.json`, which now holds the first real run against it: one applicable platform, a partial run set whose measurements, raw artifacts and unobserved figures are the artifact's own, with the other platforms left declared untested, so the choice stays `investigating`.

The bar is not the contract's own statement of it, and not the contract's to locate either: the choice's record names the `proof_section` of its accepted text — the text the ledger pins by SHA-256 — that says what a proof of that choice must do, and the contract answers every clause of that section. An answer is an obligation this contract declares and a run has to exercise, `method` or `measurements` where the clause is about how the proof is run rather than what it exercises, or an `elsewhere` naming the issue that owns a clause belonging to the decision's wider acceptance. The clauses are the record's own, split at its sentence and semicolon boundaries, and each answer carries the clause's own words as *the record* states them: the words are read back against the accepted text, which the ledger pins by SHA-256, so a clause's identity is the accepted sentence rather than its position in a split the record's punctuation decides: an answer names the clause it was written for, and an amendment to the record that renumbers that split — one clause removed, one added, the count unchanged — is refused naming the words it no longer states and the clause nothing answers, where a positional list silently re-paired every answer after the change while every rule stayed green. The accepted text stays the one readable authority — what the contract holds is a quotation that is refused the moment it differs from it, not a second copy that can drift — and the contract has no field in which to name a bar, so it cannot pick the clauses it is settled against out of the record belonging to the choice. Every obligation the contract declares must answer a clause too.

What those rules do not decide: an answer is the contract's claim about which clause an obligation covers, and the rules check that every clause of the choice's section is answered, that every obligation answers one, and that the words each answer carries are the accepted clause's — not that the carrier's wording really covers those words, which is a human's reading and the check #173 owns. So an answer can still be re-answered at another declared obligation, at `method`, or as `elsewhere`'s with a reason, and the bar is smaller without any rule refusing it: that edit changes the contract's own claims, visibly in the diff, rather than shrinking the bar the way an obligation dropped while its clause is left hanging is refused. What carrying the clause's words changed is that the claim is now legible at the site it is made — the words being answered sit beside the carrier that answers them, so a re-answer shows both halves of the change rather than an ordinal whose meaning the reader has to reconstruct — and that a claim whose words the record does not state, or which the record states twice, is refused rather than read. Which section is the bar is the same kind of claim one level up, and it belongs to the choice: the record names it, and a contract has no field in which to name or move it. No rule decides it either, and #608 established that as a checked statement rather than an opinion. **What detects a move, and the only thing that does:** `the_committed_choice_names_the_section_its_bar_comes_from` in this crate's suite, which pins the committed heading by name and asserts that section's clauses are answered clause by clause — re-pointing the record at `## Remaining acceptance` and re-answering the contract against its five clauses leaves the map at `0 refusals` and fails that one test and nothing else, reproduced and re-reported in #608. **What a reader must compare:** the choice's `proof_section` in [`decisions.json`](../architecture/decisions.json) against the section of the accepted record that states the workload — the published map prints no bar, so a maintainer surveying maps sees nothing; and once a choice is settled, a re-answered contract also breaks the result's `contract_sha256` binding, which `a_run_measured_against_a_moved_threshold_does_not_settle_the_choice` refuses, though that binding exists only after a settlement and this choice is open. **Why no rule reaches it:** which section of an accepted record states what a proof of that choice must do is a reading of prose, and ADR-0001 designates no section of its own — it states six and names issues, not sections; the mechanical proxies fail on the real record, because `## Remaining acceptance` names #38 in its own words too, so *the bar must name this choice's issue* would not refuse the move; and a hash of the named section, or an echo of it on the contract, is a second field the same edit re-records — the echo being the field #601 removed, because a contract that holds a section can state its own bar. What remains is the pin: moving the bar on purpose is an edit to a named test inside a reviewed diff, which is why it lives there rather than in prose. Re-answering a clause is the same shape one level down, and it is caught by a reader comparing the answer against the clause, because whether an obligation's wording covers a clause is judgement — #607 carried the clause's words into each answer so that comparison is made at the claim rather than from memory, and reading them back against the accepted text closed the part of that route which was mechanical (words the record does not state, words that name no one clause, and an ordinal that could be renumbered) without pretending to decide the part which is not. Both routes were registered as named items in #173's own comment thread — *answers carry the clause's own words*, taken by #607, which made each answer carry the accepted clause's words and read them back against the record, and *the bar's location pinned in the record*, disposed of in #608 with the detector, the reader's comparison and the reasons no rule can refuse it stated here rather than left implicit. The roadmap artifact is [`planning/integrity`'s](../../planning/integrity/README.md) subject and not this crate's: no entry field there carries an issue's acceptance criteria as their text — an entry records the count and pins the body by hash, and `test_validate.py` asserts the shape over every entry and holds its own exemption list to the registry — so a registration made in a thread is invisible to it, and the rule is stated and checked there rather than here. The half that says the items are in the thread cannot be read from this tree at all, and is stated rather than pinned.

A result is data too, and it is a dossier rather than an assertion: `Results` records the contract identity, the contract's fingerprint when the runs happened, the platforms left untested, and a `Run` for every platform it measured, a platform measured more than once included, because the method's repeats require it. Each run carries what the contract's own method says a run carries — the commit it was built from, the platform and version it exercised, the hardware it ran on, the obligations it exercised (named exactly as the contract names them), the outcome and any stop condition, the failures it saw, one observation per predeclared measurement, and the raw artifacts it published with their SHA-256. Nothing in that list is optional where a choice is being settled: a result that names no run, a run that names no revision, platform, version or hardware, a run that attests part of the workload or something the workload never declared, a run that published nothing, and a run that stopped without saying what failed are each refused by name. So is a result that accounts for only part of the contract's applicability: every platform the contract declares it applies to has to be measured by one of its runs or declared untested, and declaring one untested keeps the choice `investigating` — which is what stops a single-platform run from settling a four-platform contract.

Refusals, each naming its subject:

| Refusal | Why it exists |
| --- | --- |
| a contract document of a schema this loader does not read, an unknown field, or no contract at all | a contract document that cannot be read is not a checked one |
| a contract that settles a decision this ledger does not hold, or a decision that names a contract this repository does not hold | a contract nobody owns settles nothing, and an unresolved choice must point at the proof that would settle it |
| a contract and its decision that do not name each other | the path from `investigating` to `accepted` has one owner on each side |
| an obligation that names no clause of the decision, or an issue the decision names that no obligation addresses | every obligation belongs to an owner, and every owner is addressed |
| a choice that names a proof contract and no `proof_section`, or a `proof_section` and no contract to answer it | the choice names where its bar lives rather than the contract choosing it, and a bar no contract answers is not a bar |
| a `proof_section` the choice's accepted record does not state, an answer whose words that section does not state as one of its clauses, or words that are stated twice by it | a bar read from a heading nobody wrote, from words the record does not state, or from words that name no one clause, is not the accepted bar |
| a clause of the accepted bar that nothing answers, an answer naming an obligation the contract does not declare, an answer naming two carriers at once, or an `elsewhere` naming an issue the choice does not own or no reason at all | the bar is the accepted record's, so dropping an obligation from the contract, or pointing a clause at something the contract does not hold, is refused rather than absorbed |
| an obligation the contract declares that answers no clause of the accepted bar | the contract may not widen the accepted bar either |
| a decided choice with no run committed, or a run that cannot be read | a result with nothing in it settles nothing |
| a result that records no run | a choice is settled by measurements, not by an empty file |
| a run that names no platform, no version, no hardware, or no revision | a figure with no platform, no stack and no machine behind it is not a measurement |
| a run that attests an obligation the contract never declared, or does not attest one it did | the workload a candidate was measured on is the contract's workload, not a subset of it |
| a run that published no raw artifact, or whose cited artifact is absent or changed | raw data is content-addressed and must exist, so the hash path carries weight rather than decorating an empty list |
| a run that stopped on a condition the contract never declared, or without recording it among its failures | a stop condition is the contract's, and a stopped run says what failed |
| a run that names the platform it exercised as untested | a run cannot both measure a platform and leave it pending |
| a result that leaves a platform the contract applies to neither measured nor declared untested | applicability is the contract's data, so a result has to account for every platform it applies to rather than only for the ones it happened to measure |
| a result that declares a platform the contract does not apply to untested | the untested list names what the contract applies to, not what the author wants to shelve |
| a contract that names no platform it applies to, or names one twice | a contract whose applicability is not stated once, as data, can be settled without covering anything |
| a result measured under another contract, or under another fingerprint | a threshold cannot move under a result measured against it |
| a run that ended on a stop condition, left a platform untested, omitted a predeclared measurement, recorded one twice, observed above its maximum, or observed something the contract never predeclared | a choice is settled by evidence that meets the contract, not by evidence that is near it |
| a decided choice that does not cite its own run as evidence | the acceptance rests on the measured data, content-addressed with the record |
| a raw artifact a run cites that is not in the tree, or has changed since | published raw data is content-addressed, not described |

What this does not claim: the ceilings are this repository's predeclaration for #38's spike, written before any candidate run so no measurement can choose its own bar — #38's owner may amend them while no result exists, and the fingerprint ties each result to the thresholds it was measured under, which proves the bar did not move rather than that the numbers are the right ones; that an obligation's wording covers the clause whose words it carries is human judgement — the words themselves are the accepted record's and are read back against it, so what is claimed is legible and cannot drift, but nothing here decides whether the claim is true; no rule requires a decision to name a contract, so a pass that removed both the fields and the document — and the real-tree tests that pin them — would go unnoticed, while unlinking or deleting either one alone fails a test; a run's figures, its exercised workload, its platform strings and its untested list are read by this layer as the run wrote them, so what is checked is that the contract's applicability is *accounted for* — every platform it applies to is measured or declared untested, and a declared untested platform keeps the choice pending — rather than that the measurements are what they say they are; the applicable platforms are this repository's own data, and what holds that data to the bar is the clause that sets applicability — the accepted record's own words, which the ledger pins and the answers carry — read by `the_committed_contract_names_the_platforms_its_own_clause_names_and_its_prose_defers_to_them` in this crate's suite, which finds that clause by the platforms the contract declares, reads the platform families out of it, out of the obligation answering it and out of the declared platforms themselves, and requires the three to be one set: measured by moving the document, a contract applying to a fifth platform, one applying to `FreeBSD 14 amd64` where the clause names macOS, one that stopped applying to macOS while four strings remained four, and one whose obligations and declared workload dropped macOS were each accepted by the count this case used to assert — three of them silently — and are refused by name now, the platform the bar names and no run accounts for and the platform applied to and named by no clause each printed where the case names both directions; a contract whose platform list no answered clause can be read from is refused rather than compared against nothing; a family is a word carrying a capital letter — the convention the clause and the labels are both written in — so a platform spelled in lower case names no family and is refused as unaccounted for rather than read past, and the count is derived from that comparison rather than kept in step by hand; the obligations are also written in ADR-0001's proof contract, in `planning/technology-amendment.md` and in `docs/proofs/linux-shell.md`, and what this layer reads is the choice's own record and the contract: the clauses come from the accepted text, so an obligation dropped from the contract while its clause is left hanging is refused by a rule, the bar's location is the choice's `proof_section` rather than the contract's, so a contract has no field in which to point its answers at another part of the record — while the choice's record can still be re-pointed at another section and the contract re-answered against it, and a clause can still be re-answered at another obligation, at `method` or as another issue's (the paragraph above), which the suite catches for the committed choice by naming its section rather than by a rule and which the diff now shows with the clause's own words beside the new carrier; and the bar's numbers are compared against the contract only in the copy that states them — the ceilings the shell record writes beside its figures are held to the contract's predeclared maximums, and every measurement the committed run observed to a ceiling stated there, by a case in the crate's `document` target — while the obligations' wording in the technology amendment is compared by nothing, which #173 owns; the driver that wrote the committed run derives the obligations it attests from the fixture's own log, the untested platforms from this contract's applicability and the machine from the host, but that is the fixture's own suite and not this layer, which reads what the artifact says; and one candidate has now been run against this contract, on a single applicable platform and in a partial run set, which settles nothing.

What this does not claim: the member list and the dependency names are what cargo reports, so a dependency reached transitively through another member, or under a package name a record does not list, is not seen; a record's `draft` is the machine-readable summary of the text it pins, and the check compares that text's hash rather than the summary against it; an issue reference names the canonical owner without resolving its live state offline; `reviewer` records who stands behind an observation, and no independent review of these records exists in this repository; and the Host does not consult this ledger at run time yet.

## Trust and applicability

These APIs enforce transitions inside this library, not authentication or filesystem security. The future Host must authenticate the caller before supplying Authority, independently verify evidence contents/hashes/reviewer provenance, validate source authority, persist the audit journal transactionally, and call `require_ready` before dependent execution. Merely presenting a HTTPS source or SHA-256 string is not evidence verification. JSON records and fixtures do not prove framework behavior. Registry state is deliberately not exposed for arbitrary mutation/deserialization into trusted accepted state.

Pure contract tests cover normal transitions, rejected worker acceptance, high-cost exceptions, stale optimistic edits/retries, immutable accepted records, atomic competing supersession, selective fact expiry/revocation, round trips and invalid thresholds. These are platform-independent policy tests; operating-system process interruption/recovery, external evidence fetching, access control, graph query integration, UI accessibility, durable migration/rollback and live runtime compatibility remain with their canonical integrations. No interrupted process or lost database write is simulated and called production recovery.

## Acceptance accounting

Implemented foundational #173 scope: decision/authority/alternative/constraint/evidence/reversal/supersession schemas; proof contract; fresh version pins; refusal gate; machine-readable affected artifacts; draft and accepted lineage behavior. Source/issue/requirement/graph/deployment links are representable.

Now enforced for the shell choice: its proof obligations are a committed contract with predeclared ceilings, a run of that contract is the only thing that can settle it, and an untested platform or a triggered stop condition keeps it open.

Now enforced in this repository: ADR-0001's decisions are recorded as data — `ADR-0001/HOST-STACK` accepted on explicit client authority, `ADR-0001/DESKTOP-SHELL` and `ADR-0001/GRAPH-STORAGE` investigating under #38 and #233 — the accepted text and the client instruction that authorized it are content-addressed, every workspace member is recorded and pins the accepted stack constraint, and the one artifact that reaches a choice still under proof (`crates/symbiote-desktop`, through `tauri` and `tauri-build`) publishes `provisional` rather than `settled`. A provisional choice cannot reach a member unrecorded, and a new workspace member cannot be added without a record. No compatibility fact is recorded, because ADR-0001 certifies no version: #38 and #233 own the measurements that would create one, and a fact must be fresh and verified wherever it is pinned.

Still pending: authenticated Host enforcement (`require_ready` has no product caller yet; #180 and #181 own it), durable accepted-history/audit persistence and recovery, a recorded transition history rather than each decision's published state and one replayed draft revision, measured #38 workload, automatic research refresh and authoritative source verification, graph/issue-generation integration and an immutable content-addressed artifact store. Existing ADR-0001 remains accepted client direction; its provisional choices cannot pass a fabricated compatibility fact. #173 remains open until these obligations are accounted for through real integrations.
