# Dispatch preparation: composing scheduling, routing, leases, worktrees, providers

Canonical owner: [#205](https://github.com/RepairYourTech/SymbioteIDE/issues/205) and [#189](https://github.com/RepairYourTech/SymbioteIDE/issues/189) (Dispatch aggregate), depending on the merged slices: Role routing (#204), dependency edges (#94), task leases (#95), reserved worktree locations (#211), and the provider registry (#464). This slice adds the durable **composition** record — the point where all five primitives meet. The live `Dispatch` runtime contract and `Start` transition existed since #184; what was missing is the journaled, explainable preparation that decides *what* may be started and *why it was refused*. The worker loops (#465 native, #464/#465 external) consume this record next.

## The preparation record

`prepare_dispatch(task_id)` runs entirely against authoritative storage — no client-supplied composition — and journals one `dispatch_prepared` event per task (latest wins, table replays exactly, both directions audited):

- **Scheduling** — the task must be `Ready`; the #95 projection's dependency and stream-safety conditions are enforced again at Start time (not in the preparation itself).
- **Routing** — the latest route decision (#204 slice) for the task's origin work identity supplies the resolved Role; unresolved routes are recorded as such.
- **Lease** — informational: whether a lease is already held (renewal scenario). First-time starts acquire the lease transactionally during Start; the fencing token is minted at start.
- **Worktree** — the stream's reserved worktree identity and branch from the Change Stream record (#211 slice owns filesystem reservation; this records the binding).
- **Provider** — the routed Role's workforce binding (#203/#486) carries the runtime profile; the connection, billing entitlement and model descriptor that profile names must all exist in the #464 registry *and* the SDK registration contract (`symbiote_runtime_sdk::provider::validate_registration`) must accept them at preparation time: consistent profile/connection/entitlement/model identities, a non-empty endpoint reference, a valid model descriptor, an unexpired entitlement, and a supported authentication/billing mapping (native Symbiote never binds harness-managed subscription). A registration that is absent or inconsistent earns no provider step and records a typed refusal — `unresolved_profile` (no workforce binding resolved for the Role), `missing_connection`, `missing_entitlement`, `missing_model`, `binding_mismatch`, `expired_entitlement`, `unsupported_authentication_billing`, `invalid_descriptor`. The profile's declared connection and model identities are recorded either way, so a refusal names what it refused instead of hiding it. Credential *material* and verified endpoint locality are execution-time Host concerns (#217) and are deliberately outside this check. The same check is re-run at the two later boundaries, because a registration is live state, not a fact fixed at preparation: **start** re-validates it before a dispatch is compiled, and **activation** re-validates it before any worktree or transport side effect. An entitlement that expires — or a connection whose authentication/billing pair is replaced — while a dispatch is Running therefore refuses the run rather than executing it. All three boundaries resolve through one implementation, so a registration cannot be valid for one and invalid for another, and all three report the reason in the one vocabulary below.

The outcome is `ready` only when scheduling, routing, and a validated provider registration all resolve. **A refused composition is recorded like a ready one**: the response body carries `outcome: "refused"` with the refusing step — refusal is a successful read of recorded state, not an error. Failures *outside* the enumerated steps (unknown task, unreadable origin, malformed stored binding) surface as errors and leave no preparation record; the journal's surrounding events remain the evidence for those.

## Authority

`prepare_dispatch` and `get_dispatch_preparation` are local-owner operations, consistent with the scheduler endpoints; restricted worker identities arrive with #269. The preparation record carries no secret values: provider identity is a connection reference, and credential materialization stays with #217.

## Starting from a preparation

`start_prepared_task` (protocol v1.11 `start_prepared_task`) consumes a `Ready` preparation in one transaction: it re-verifies the routed Role still exists, re-validates the profile's provider registration against the registry (a registration that lapsed since preparation refuses with `failed_precondition`, and no dispatch is compiled), refuses when a live lease from a previous generation is held, compiles the live `WorkforceRuntimeContract`/`Dispatch` via the domain `Dispatch::compile` (Role record, workforce binding, profile, and the Host record with its enforcement claims), applies the domain `Start` transition, and then **acquires the governing lease in the same transaction** — the fencing token is minted at start, journaling a `task_leased` event under a `<command>-lease` id. First-time starts can never pre-hold a lease (leases exist to fence Running dispatches), so the preparation's lease step is informational for renewals. The response carries the started dispatch identity, stream, and fencing token. Compilation also records the candidate's resource limits on the contract (validated against the contract's own bounds, at compilation and on replay), because the execution the start produces is bound by them: activating the dispatch reduces the recorded limits to the bound the Host applies to every process the dispatch's tools run in, and a declared limit the Host has no kernel bound for refuses the run with `failed_precondition` naming the declared field — a second activation-time precondition beside the recorded-state vocabulary below, checked before any worktree or transport exists and never a silently ignored limit. Contracts journaled before limits were recorded deserialize without them and refuse activation for having no bound to apply, rather than breaking replay or running unbounded. [Workforce bindings](workforce-bindings.md) owns which limits are enforced today.

## One refusal vocabulary

The answer to "why can this dispatch not run?" is one name at every boundary, because a refusal carried in three shapes would leave the product surface showing whichever shape is weakest. `start_prepared_task` reports every refusal in the dispatch-refusal vocabulary: a refused preparation reports the reason *it* recorded (`not_schedulable`, `unrouted`, or the provider reason its provider step names), a Change Stream that is no longer `Active` reports `stream_inactive`, and a registration that lapsed since preparation reports the registry's own reason. Provider reasons are the `ProviderRefusal` names unchanged — `unresolved_profile`, `missing_connection`, `missing_entitlement`, `missing_model`, `binding_mismatch`, `expired_entitlement`, `unsupported_authentication_billing`, `invalid_descriptor`, `unsupported_version` — so a name means the same thing at preparation, at start and at activation. The protocol error is `failed_precondition` whose message is `dispatch refused by recorded state (<name>)`: the code is the category, the name is the answer, and nothing in it is an input value or a path.

The record and the vocabulary cannot drift: the domain `validate`s that a `Ready` composition records no refusal and that a refused one records at least one, so a refused preparation always has a reason to report rather than a bare outcome, and the recorded provider step and the start's error are two readings of the same name.

The Host record's enforcement claims are operator-provisioned for the Host's own inventory identity (the service refuses a host identity that is not its own); claim windows are bounded, and the evidence ids are Host-derived, not client-supplied. A refused preparation (`failed_precondition`), a superseded preparation, or a second start all fail closed — the task stays Ready and no lease exists. The Host record also advertises its supported runtimes: `NativeSymbiote` always, and `ExternalHarness` only when the operator provisioned the external execution path (the explicitly labeled in-process fixture harness transport, or the operator-configured sandboxed harness program the Host launches under the dispatch's declared memory ceiling; a live pinned-binary path stays gated on explicit user authorization for credentials and billing). Without that provisioning, a binding whose profile is `EXTERNAL_HARNESS` refuses at start — never a silent fallback to the native runtime. The two-harness demonstration (#269) drives both lanes on ONE project through this composition: native and external workers with their own bindings, objective/task/stream identities, and worktrees, with the external profile's credential reference unregistered at the broker and no `UseCredential` grant, so configuration and credentials cannot cross. The Project-isolation demonstration goes further: TWO projects on ONE daemon, each with its own repository, team, bindings, and streams. The workflow driver parameterizes the demo flow by project lane (`DemoLane`); role and root ids are globally unique across the daemon, provider connections and model descriptors are Host-global records, and the broker refuses a credential reference registered for a different project (`cross_project_denied`) — the demo drives the leak attempt, the operator's revision-CAS binding correction, and the corrected run.

Least privilege at assignment (first #269 core): `Dispatch::compile` attaches an immutable `effective_access` snapshot to the contract — the binding's authorized access narrowed to exactly the Task's Root — and consumers (sandbox tool consent, context resolution) enforce the narrowed snapshot, not the Role's whole scope. The binding's declared per-control `minimum_enforcement` floor is binding at assignment: a Host claim weaker than the floor refuses the start (`unsupported_control`), so re-staffing/fallback recompiles and rejects rather than inheriting. Scope honesty: only ROOTS are narrowed — permission grants are not (they gate which per-permission controls are required, and the credential broker is project-scoped with profile-reference bounding, so a narrow-root worker with `UseCredential` may still resolve any profile-referenced credential of its project). Two upgrade semantics: `minimum_enforcement` was previously declared-and-validated but never read, so activating it means existing bindings whose declared floors exceed their Host's claims will newly refuse starts; and contracts journaled before this change deserialize without `effective_access` and fall back to their full compiled binding snapshot.

## Evidence and remaining acceptance

Covered by store tests (composition steps, refusal recording, replay, readback, unknown-task refusal, and the provider registration refusals above) and daemon tests (projection → prepare → refusal recorded → replay identical → restart replay → journal lineage; every unusable registration — absent connection, absent entitlement, absent model, expired entitlement, a model registered to another connection, and an unsupported authentication/billing pair — preparing as `refused` with its own reason, refusing the start by that same name, and leaving the task Ready; a start of a refused preparation naming its recorded reason at the store boundary and, through the CLI, on the wire; and a registration that lapses after preparation or after start refusing the start and the run).

Pending #205 acceptance, tracked in the issue: mixed-runtime staffing round-trips; and the remaining #269 scope: skill/MCP/secret-scope trust metadata, mid-run policy change semantics, per-denial enforcement-layer reporting. Both worker loops now emit elevation *asks* through the Host (`file_elevation_ask` / harness refusal mapping): a native `use_credential_not_granted` refusal and an external harness capability request are journaled as `ElevationRequested` evidence and never license a permission; only a later owner `decide_elevation` can. Decisions license exactly the permissions that have enforcement consumers: `UseCredential` (the broker's lease gate) and `ExecuteProcess` — the native shell-tool path resolves its current policy through `resolve_shell_access`, which widens the binding access with `ExecuteProcess` only while an owner-decided lease for THIS dispatch is active at the run's clock, and the sandbox independently re-checks every grant it requires. They license exactly the dispatches whose runtime has the consumer: both gates live on the NATIVE loop, so a decision on an `EXTERNAL_HARNESS` dispatch refuses as `InvalidElevation` whichever permission it names (the harness never consults `active_elevation` — its escalations are refused by the driver regardless of any lease). An ask never widens; expiry and sticky revocation stop the widening at once. Deciding a permission with no enforcement consumer (still `MutateStream`, `Network`) refuses as `InvalidElevation`.

Applicability: security/privacy — owner authority only, no secrets, refusals recorded as evidence. Accessibility not applicable to a headless composition layer. Performance bounded by per-task record count. Linux-first, matching the Host.
