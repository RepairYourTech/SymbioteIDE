# Offline roadmap integrity

This Python standard-library maintenance tool validates an immutable GitHub REST issues snapshot and generates a structural registry and topological index. `validate.py` reads a file and writes a directory and reaches no network at all; the only issue-mutation path here is `regenerate.py`'s `apply`, and it mutates only through a runner it is handed — `CliRunner` for an operator, a recording fake in every test. Python is used for existing planning maintenance; this does not select the product runtime.

```sh
python3 planning/capture_roadmap.py --help
python3 planning/integrity/validate.py /path/to/issues.json --output /path/to/generated
python3 planning/integrity/regenerate.py plan --base old.json --live now.json --amendments amendments.json --output plan.json
python3 planning/integrity/regenerate.py apply --plan plan.json --live now.json --repository owner/name --dry-run
python3 planning/integrity/test_validate.py
python3 planning/integrity/test_validate.py --snapshot /path/to/issues.json
python3 planning/integrity/test_regenerate.py
python3 planning/integrity/coverage_ledger.py --check
python3 planning/integrity/test_coverage_ledger.py
python3 planning/integrity/test_revert_rules.py
python3 planning/integrity/revert_rules.py
```

Input is a JSON array with REST `number`, `body`, `labels`, `state`, `state_reason`, and `updated_at` fields. Pull requests are ignored. Canonical issues require `planning:canonical`, one `symbiote-plan-key`, and one `symbiote-plan-revision` marker. Reference entries require `planning:reference`, `symbiote-reference-key`, and a direct `Canonical owner: #N`; the historical program entry uses `symbiote-program-entry` and its explicit canonical roadmap link. Unclassified keyed issues remain outside the executable graph.

Atomic tasks require one parent epic, one wave, and one explicit `## Dependencies` section. Each dependency line must be `- #N` or a same-repository GitHub issue URL. Empty/unknown syntax fails; no prerequisites must be explicitly written as `- None` (the existing constitution sentence is also supported). Related/review/integration sections never create edges. Historical details in references cannot create metadata or edges; canonical bodies are parsed in full.

Checks include duplicate canonical keys, missing revisions, issue existence, canonical dependency targets, archived/not-planned prerequisites, cycles, later-wave prerequisites, body/label wave consistency, reciprocal epic membership, master epic membership, and any declared master/child counts. Closed completed issues remain represented; ordering does not establish readiness. Generated records preserve original body SHA-256, update timestamp, labels, and state. The snapshot SHA-256 identifies the exact source capture. No entry field carries an issue's acceptance criteria as their text: an entry records how many such items the body states (`acceptance_items`, an integer) and pins the body by hash, so a collection appears in an entry only where the roadmap itself defines one. The exemption list lives in `test_validate.py`, which holds every name on it to the registry — a name that is not a collection in each entry that carries it fails there rather than covering the entries it exempts, since a field that cannot trip the rule needs no exemption from it — and asserts the shape over every entry, #173's among them, since that is the entry the architecture contract's bar registration names. Work registered in an issue's own thread rather than in its body is therefore invisible to this artifact and to everyone who reads it, and the body itself is pinned by hash rather than edited in place, so a later reader has to read the issue; that is the shape this file owns, and it is why the contract doc points here for it.

The committed reduced audit fixture reproduces the structural inputs from the after-audit capture; its `source_body_sha256` fields refer to original full bodies, not the deliberately reduced fixture bodies. Default tests compare its full graph, mapping, waves and counts to the generated original-snapshot registry. `--snapshot` additionally checks the full 466-issue audit capture and injects a duplicate-key regression. This optional check is pinned to that audit, not an arbitrary future inventory.

## Accepted-decision coverage ledger

#443 reconciled the live inventory against the accepted discussion and recorded one coverage matrix: a section per accepted capability family, naming the canonical issues that own it. That matrix existed only inside a build artifact, which expires, so the reconciliation it certified could not be read in this tree and nothing could tell whether it still held. It is now `fixtures/audit-2026-09-07-coverage.md` — that artifact's `coverage.md` byte for byte, its hash, the archive's hash and the artifact's expiry (`2026-10-07`) recorded as the ledger's provenance, since after that date nobody can recompute the archive's — and `generated/coverage.json` is the ledger derived from it and from the committed registry: each family's owners resolved against registered work, the totals the audit recorded checked against the registry's own, and the canonical atoms no family claims named rather than left to be inferred.

The ledger adds no reading of its own to the registry's: every figure it records, and the audited totals it checks, are counted from the registry's entries by the classes `validate.py` owns, so a registry that miscounts itself cannot make the ledger repeat the mistake. The audit's revision counts — 241 canonical atomic issues, 19 epics, 198 references, 702 canonical prerequisite edges — are held as data, so the moment the registry moves past the revision they were reconciled against the check fails naming the movement, and the coverage has to be re-derived instead of carried forward. `--check` fails unless the committed ledger is what this tree emits, and both modes refuse a ledger that is not true of the registry first, naming the untrue claim rather than only reporting drift.

Refused by name: a family with no name or no owner, a family named twice, an owner the registry does not hold or holds only as a reference entry, one owner named twice by one family, a registry whose declared counts disagree with the entries it holds — class by class, and with its entries and unkeyed issues required to account for the snapshot it names — totals that are not taken from those entries or not the audited revision's, canonical work that declares no acceptance item, a ledger whose unclaimed atoms are not what these families leave unclaimed, and a committed ledger that is not this tree's.

It covers 28 families and 196 named owners over the 241 canonical atoms, and **47 canonical atoms are claimed by no family** — the ledger names all 47 rather than letting the gap be inferred, because the matrix covers the accepted families and never claimed the whole inventory. Of #443's own completion evidence this makes two items readable here — the coverage matrix over all 28 families, and that canonical work carries acceptance and verification criteria — while the dependency graph and order are what `validate.py` checks, and the audit's apply/idempotence and read-back runs remain its artifact's record rather than this tree's. One limit cannot be closed by any checker here: the families are the audit's reading of the accepted discussion and this repository holds no conversation corpus, so the tool proves the matrix is internally sound, that its owners are work the registry holds and that it still agrees with the registry — **not that the 28 families are the right ones**.

## Pull-request closing keywords

`closing_keywords.py` reports the issues GitHub's parser will close from a pull request's description and from the messages of its commits, which GitHub scans equally and with no reading of negation. Two rules follow.

A description fails when a closing keyword is negated by its own sentence, or when the keyword is buried in prose instead of stated as its own clause: `Closes #54` is a closure both GitHub and a reader can see, while "the defect that closed #54 is fixed" is a remark that closes the issue anyway. The rule is precise rather than trigger-happy: of the 85 descriptions merged up to `40a43b2d`, exactly one trips it — PR #530, whose first line disclaimed the closure it performed one second after its merge.

A commit message (`--commits`) and a pull-request title (`--title`) fail on any closing keyword, because GitHub reads both on merge and no reviewer reads either as a closure statement. The title matters because this repository squash-merges with `squash_title=COMMIT_OR_PR_TITLE` and `squash_message=COMMIT_MESSAGES`: a pull request whose branch carries more than one commit merges with its title at the head of the merged message. That is not hypothetical here: of the 85 pull requests merged up to `40a43b2d`, 49 carried more than one commit, so their titles head the merged messages, and 44 have a subject that is exactly that pull request's own title with its number appended. The title rule refuses none of the 85 merged titles, including the house style that cites issue numbers in parentheses (`(#229, #464)`). PR #551 landed this guard and was itself caught by the commit channel: its final sentence, "the defect that closed #54 is reproduced rather than described", closed #54 when the pull request merged. The tests pin that message, the two real descriptions and two real titles, and the documented syntax.

Every count in this section is a snapshot of `main` at `40a43b2d`, not a property of the history: it grows with each merge, so a re-measurement should read the then-current `main`.

Keywords count only against the default branch, so a non-default base is reported as closing nothing rather than failing.

## Driven-binary source records

`source_record.py` checks that a driven binary's embedded record covers what its own build read. The end-to-end proofs run workspace binaries, and each binary carries a record of the inputs its build compiled (`symbiote-source-stamp`); the proofs compare that record against the tree, so a proof cannot run against a binary built from other sources. What no proof checks is whether the record *covers every input the compiler read*: if a new way to compile a file appears and the walk does not follow it, the record is quietly short, every proof stays green, and only an audit finds it. That happened here — the walk did not follow `#[path = "…"]` module attributes, and `crates/symbiote-store/src/tests.rs` was compiling six files the record named only for packages that happened to be walked anyway. Several of the findings since are in the suite rather than only in an audit: `crates/symbiote-source-stamp/tests/record_guard.rs` builds a fixture with the real cargo that is running the test and puts both readers to the bytes that build produced — a module the compiler found under a name the walk skips, a record with one line removed, a build driven into a directory of its own inside the workspace, and units that carry one crate name — so a regression in what the record covers fails there, in a minute, instead of surviving until the next audit. The facts the hand-written fixtures used to state for cargo are taken from a real build too, in `planning/integrity/test_source_record_real_cargo.py`: which unit produced an artifact, which package a same-named unit belongs to, and that a build's own target directory is excused where it was *given* rather than by the name `target`. It reads no record — what it asserts is what cargo wrote — and it skips, with the reason, where no cargo can be run.

The first half is completeness against rustc, and the oracle is cargo's own per-unit dep-info, written by rustc for each unit that produces the binary. The record's implementation never reads it — its module documentation says why: it is a private, versioned binary format written *after* the build script that must write the record, so it can neither populate a record on a first build nor be an input the documented rebuild could clear. A check that runs after the build has neither problem. Which package a unit belongs to is read from cargo's own fingerprint of the unit's hash rather than from the crate name its dep-info file is spelled with — measured on a two-package workspace whose targets collide, `deps/guard-cf49597cb80e0847.d` and `deps/guard-25d04fabbb313b6d.d` differed in nothing but the hash, and a name-only reading credited the other package's unit to the driven one: it satisfied the requirement that a green rest on a unit of the driven package's own build — what `cargo clean -p <package>` leaves is exactly that state — and it was compared as one of the driven binary's closure, which reported its own source as an input the record does not name. A dep-info no fingerprint places, or one more than one fingerprint names, is not an identity and is not counted at all. The package and even the target are still not the unit: cargo's own uplift names it, because it writes the unit's output into `deps` and gives the profile directory a name for that same file — a hard link where the filesystem allows one, a copy where it does not — so the file in `deps` sharing the binary is the unit that produced it. Measured on this workspace, `symbioted` shares its file with exactly one output out of the 11 units whose fingerprints name its `bin-symbioted` target, and those 11 are not the same evidence: ten of them read 7 workspace files and one reads 10, and a stale one names a generated record written by a different build-script run of the same package. Where that relation is not there to read — a platform that copies the artifact rather than linking it, a binary no target directory wrote — the tightest identity left is the target the artifact is named after, which is still narrower than the package and than the crate name. Cargo's *merged* dep-info for a binary is **not** usable for this: it also carries the build script's `rerun-if-changed` declarations, so it echoes the record back and agrees with it by construction. Two sets of inputs are excused, and only two: registry sources outside the workspace, as the record documents, and everything under the build's own output directory — the directory the check was *given* (`--target-dir`, cargo's `target/<profile>` or whatever a build was driven into), because cargo wrote it and the build script that wrote it is named by the record. Measured, a build driven into `<workspace>/build-output` left 353 inputs under it that no record can name, and a rule that excused the name `target` instead refused the binary for every one of them. The directory names a *walk* skips are the walk's rule rather than a check's — which names they are, and where each applies, is `crates/symbiote-source-stamp/src/wire.txt`'s, and no copy of them is kept here — and a check skips none of them, because it is handed the evidence of what each unit read: where a unit read a file under one of those names, skipping it hid a file the build read, which is what that rule forbids. The record owes the declaration that reaches such a file, and the check now requires it: measured, a build script's `mod tests;` puts `tests/mod.rs` in the record, a check that excused the name reported the record clean with that line removed, and one that excuses nothing by name refused it. The walk's own skips stay the file's, and the record still follows the compiler where the walk does not — a plain `mod name;` is resolved to the file rustc looks for, `name.rs` and `name/mod.rs`, in each directory the declaring file could be resolved against. Measured before that was followed, `mod target;` compiling `src/target/mod.rs`, `mod node_modules;` compiling `src/node_modules/mod.rs` and a package-root `tests/mod.rs` that `build.rs` declares were dropped from the record while both readers reported the binary current. This check is only as good as the dep-info it compares against, so it refuses rather than passes where the unit that produced the driven binary left none: measured, against a target directory holding no dep-info at all — what `cargo clean` leaves — it reported OK having read 0 units and 0 inputs, so a record nothing was compared with was called complete; and measured with only another compilation of the *same* bin target left, the pre-slice check read 9 units and 5 inputs from a build whose read set omitted a module the driven build compiles, and called the record complete.

The second half covers the inputs cargo reads rather than rustc: the record must also name, for every package in the binary's closure, its own manifest and, for every workspace root cargo can resolve for it, that root's manifest and lockfile. No per-unit dep-info names them — measured on a build-only target directory, the rustc oracle names none of them, so dropping one from the record passed this check before this half existed — so the packages come from `cargo metadata` and their roots from the tree: the root a `package.workspace` names, or else each ancestor manifest declaring `[workspace]` and the package's own directory, which is the root of a package its workspace `exclude`s. A workspace manifest is the sharp case rather than a formality: its members say `edition.workspace = true` and `version.workspace = true`, so its content decides what they compile as while every `.rs` file stays byte-identical, and a bump of `version` is refused by nothing else, since no source in this tree reads `CARGO_PKG_VERSION`. A path dependency may belong to a workspace of its own — `crates/symbiote-workflow`'s fixtures are compiled from outside their package, and a probe dependency in a second workspace was how the record's own gap was found — so each package is asked about *its* roots, not this one's. The nearest ancestor is not enough: measured, cargo resolves a member to the workspace the build was invoked in, which can be an *outer* manifest that a nearer `[workspace]` manifest sits below, and the nearer one is then never loaded. A name settles it: measured, a package whose manifest says `workspace = "../root"` resolves to that root even where an ancestor manifest declares `[workspace]`, reads an inherited path from the named root, and is refused with `member of the wrong workspace` by a build that both nests it and claims it as a member — so such a package has exactly one root.

A configuration file that exists and is not named, or a named one whose content moved or that has gone, and a record that names no `env:CARGO`, are failures too — the build configuration is what the record cannot watch without making cargo relink the stamped crates on every build.

The wire the record is spelled on — its framing and the encoding of the bytes it frames, the division of a record into lines, the one environment variable it pins, the contents an input is given, what a record *line* is, every mark with its remedy and its precedence, and what to say about a mark the file does not name, a line it cannot read or a record it cannot decode — is one file, `crates/symbiote-source-stamp/src/wire.txt`. The crate embeds it and this checker reads it, so the two cannot disagree about what a record says: changing a mark, its remedy, its precedence, the shape of a line, where a line ends or what a record's bytes are is an edit there alone, and a reader that met an unknown mark's order it does not implement refuses the file rather than picking one of its own. Both readers take a record out of a binary by that file's framing and decode it by its encoding, so neither decides for itself where a record begins, where it ends or what its bytes are — the `end` that ends a record follows the LF its last line ends with, so a marker the record's own bytes spell does not end it, and a build refuses to stamp a locator a record cannot hold — one holding a line feed, a carriage return or either marker — and an artifact the wire cannot read is refused in the file's remedy rather than raised over by one reader and reported as carrying no record by the other: bytes that are not that encoding are named with the byte they stop at, and a record whose own bytes spell a marker is refused rather than read short (measured: such a locator made both readers drop every line after that marker and report a binary as matching a tree it was not built from). The rule itself, in its own order, and the measured disagreement each step of it settles — a line with no locator, a blank line, a line carrying a CR, and a content that is neither a hash nor `unset` among them — are stated in that file rather than restated here.

A record that cannot be stood behind is refused rather than compared, and the mark says which fact its build could not establish. One mark is written where no reading establishes the workspace cargo resolved in; the other, `cargo-not-asked`, where the *cargo that ran the build* could not be run at all — `CARGO` named a program that cannot be started, so the two things only cargo answers went unasked: the workspace a run directory names (`cargo locate-project`) and the closure cargo resolves for the package there (`cargo tree`), the second of which is what gates the walk's closure. Reading either failure as "nothing here" would record a root list, and a closure, that nothing checked, so the build marks the record and both checkers refuse it, the refusal asking for a cargo that can be started and a rebuild that stamps again (the build script declares `CARGO` as a rerun input when it writes that mark, as it declares `PWD` for the other). The readings are the directory the invoking cargo was started in, the manifest its command line named — including the arguments a cargo alias expands to, since a build reached through one names no manifest on its own command line (measured: `[alias] b = "build --manifest-path ../sibling/member/Cargo.toml"` runs from a parent whose command line is `["…/bin/cargo", "b", "--offline"]` while the sibling's fork is what links) — the build directory and the shell's `PWD`. The process's two readings are what close the arrangements that used to hide: a launcher that sets cargo's working directory and leaves `PWD` inherited, a build told `--manifest-path` into another workspace with its build directory outside every workspace, and the alias above — each used to leave the record naming the wrong workspace's `[patch]` fork while a change to the fork the binary was compiled with was reported clean. A mark is read by its content rather than by its name — an `unset` under a locator no mark is written with — so a record an older version marked is refused too, rather than compared against a missing file it matches, and a mark neither checker knows is refused with the locator it was written under rather than passed over. A build whose record carries either mark still succeeds; both `changed_sources` and this check refuse it and name the remedy, reporting `cargo-not-asked` ahead of the resolution where a record carries both — the cargo that ran a build is one of the readings that can name the workspace its resolution was read in, so losing it can lose the resolution with it, and the resolution's remedy alone leaves the cargo unaskable — and rebuilding from the workspace with `PWD` reported (sh, bash, zsh, git bash) stamps again and clears the resolution one, because the build script declares that variable — a declaration an ordinary build does not make. Where the platform keeps neither reading (this crate reads `/proc`, so Linux), `PWD` is all there is and a stale one is not visible to the build script: those arrangements are recorded unmarked there, and the crate's module documentation states the limit. Only a build no reading places at all — output directory outside every workspace, run directory naming none, and no manifest on the command line — stops instead of recording; a package no `[workspace]` manifest owns is its own workspace root, as cargo itself answers, so a build of one records and its `[patch]` table is read.

```sh
cargo build --locked -p symbiote-host --bin symbioted -p symbiote-sandbox --bin symbiote-sandbox-launch
python3 planning/integrity/source_record.py \
    --binary symbiote-host:symbioted \
    --binary symbiote-sandbox:symbiote-sandbox-launch
python3 planning/integrity/test_source_record.py
```

It reads and writes nothing; exit status is 0 when every input the compiler read, and every input cargo read to build the binary, is named. The `source-records` job in `Rust contracts` runs it on every pull request after building those two binaries, so a newly unrecorded input class fails the build instead of waiting for an audit; its own tests run with the rest of this directory's in `Roadmap integrity`.

This implements a bounded portion of #470. The registry accounts for every issue a snapshot holds: the counts name each class — master, task, epic, retired, unclassified, reference, program entry and unkeyed — and the suite asserts that those classes sum to `snapshot_issues`, so no issue can disappear into a class the counts do not name. The coverage ledger below holds the committed registry to its own entries on the same question — the totals it records are counted from those entries rather than from the registry's declaration of them — so a declaration fitted to that sum cannot survive that check. It does **not** read any conversation: scope discovered in discussion is not evidenced by a REST snapshot. The reconciliation with the accepted discussion that it could not certify is now delivered from #443 as the coverage ledger below, which says in its own terms how far that reaches and where it stops. Neither is acceptance completion certified (`acceptance_items` is only a checkbox inventory). The original bootstrap importer must not be used to overwrite this registry's newer issue authority.

## Regeneration

`regenerate.py` owns what happens after validation: regenerating issue bodies from the current registry and accepted amendments. `plan` takes the REST capture the registry was generated from, the current capture and the amendments, builds the intended snapshot under the next free numbers, validates it with the same `validate_snapshot` the registry is checked with, and writes a plan; `apply` performs it through a runner, or prints a unified diff per body and mutates nothing under `--dry-run`. A plan carrying any refusal is never applied, and neither is one whose mutations would leave the registry invalid: **what is written is validated against the capture it is written to**, which is why `apply` takes `--live` and why a plan file an operator edited is re-checked rather than trusted.

A key is answered by role, in one place. `key_holders` says which issues a key addresses as work and which historical entries carry it, and both the plan and the verification ask it — a key canonical work carries amends that work even where a superseded entry shares the key (in this registry 80 of 192 reference keys, covering 80 of 261 tasks), and a key *only* a reference entry carries is refused, naming the canonical issue it resolves to. Historical entry bytes are never regenerated.

Each rule is refused by name rather than left to an operator's care:

- a duplicate key, dangling dependency or cycle — no mutation is planned at all;
- an amendment declaring no base revision and body hash;
- a live revision newer than the declared one;
- a concurrent edit whose changes overlap the amendment, naming the conflicting lines, with disjoint changes merged three-way;
- a regenerated bootstrap that would drop a section the live body has, naming the lost sections;
- a create that would break epic membership;
- an amendment naming a key **only** a reference entry carries, naming the canonical issue that entry resolves to;
- an ambiguous create — a lost response, or an issue a human made first — reconciled by reading the key back, with a second ambiguity failing visibly instead of retrying blind;
- a target that moved after planning, and a read-back whose body is not the intended one;
- a plan whose mutations would leave the registry invalid, refused before the first mutation.

The suite proves the path over the whole registry rather than over a convenient key: every canonical key in the committed audit capture is planned and required to produce exactly one update, and every reference-only key is required to be refused naming its canonical owner.

`verify` then proves what landed is exactly what was planned and that every issue the plan did not name is byte-identical and in the same state. The rules are exercised through a recording fake, so what the tests prove is the rule and not a transport, and no test reaches the network. Two limits are stated rather than implied: `verify` needs both captures, so the CLI leaves it to an operator who holds them; and validation does not cross-check a reference key against a canonical key, which is why regeneration refuses a reference key itself instead of relying on validation to notice the duplicate.

## Reverting a rule to prove it bites

`revert_rules.py` is how this repository re-proves its own refusals: one row for each refusal of the architecture governance crate that has been proved by reversion, each row holding the rule, the text that removes it and the case that must fail — the text being the crate's own sources, the contract document, the committed contract data a case reads its platforms and clauses out of, or the proof record its document target compares the bar against.
A rule comparing two of those facts is proved by moving the document rather than by reverting the comparison: a comparison two honestly agreeing sides satisfy stays green when it is removed, so the row that bites there is the document's, and the labels say which side moved. The table is the proof's single home — it was four scripts under `/tmp`, and a proof that lives outside the repository cannot be re-run by anyone else, so it lives here beside the artifacts it proves. **What it does not claim is completeness:** nothing relates the rows to the crate's refusal sites, so a rule added without a row runs unproved while the report stays green, and the report is about the rows the table has rather than about the crate.

The live tree is never touched. The driver copies this working tree into a temporary directory, mutates the copy, runs each case there with the copy's own target directory, removes the copy, and fails if any byte of the live tree moved — so it can be run beside another build. (The version before this one mutated the live tree in place, and a concurrent `cargo test` reported failures that were only its mutations.) A row costs one `cargo test` in the copy, whose first build is cold.

A second table, `HOLDS`, holds the rules a reversion cannot prove because the rule *is* the refusal being reverted, or the link the refusal is about: removing the text would remove the refusal, so a mutation would watch nothing fail. Each row names its rule, the case stating it, the subject stating it, the text it states once, and each way the refusal is shown biting — the subject a line past the number it declares, the case run against a tip whose guard was smaller, a link taken out of the file it is written in, or the workflow written into one of the states `chain.py` names. The driver mutates the copy instead, requiring the subject to be in the tree, to state the refusal exactly once, and to fail under every way the row names; a row that names no way, and any of the driver's tables with no row, are refused rather than passed. The copy keeps `.git/` for the history way.

`test_revert_rules.py` holds both tables to the tree without running cargo: every anchor is text this tree holds exactly once, every named case is one a suite actually runs (not a helper of that name), no two rows are the same rule or the same mutation, and the driver roots itself at the repository it is part of. The same checks hold each `HOLDS` row's subject, the refusal it states once, the case it names and every way it lays in the tree, so un-naming that case, vacating a comparison or deleting its file fails here in a second as well as in the driver's report. So a renamed case or a moved anchor fails in a second, rather than becoming a row the driver skips when somebody finally runs it. The contract document's exception list is proved here too: a listed name the crate's own `src/` carries nowhere is refused, and one edit — renaming the definition in `policy.rs` — reaches that failure, so this direction is a row rather than a proof by hand.

## Holding the reader's own size
